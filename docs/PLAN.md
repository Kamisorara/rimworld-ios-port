### M1 运行时探针（✅ 已关闭，2026-11-21）

**结论：官方包路线成立。** `Microsoft.NETCore.App.Runtime.ios-arm64 11.0.0`（GA，混合构建）+ `COMPlus_InterpMode=2` 配方：真机完整跑通探针（`CoreCLR 就绪` → Reflection.Emit → `exit 42`），吞吐 **87.7 M 迭代/秒**（安卓 JIT 基线 ~200 的 44%，远超 20 的可玩阈值）。零补丁、零 StikDebug、零脚本，装完即玩。

机理备注：InterpMode=2 的关键作用是禁 R2R（绕开混合构建初始化里的 SIGABRT 死点，`eeconfig.cpp`：`InterpMode>=2 → fReadyToRun=false`）；测试设备（iOS 27，SideStore 签名自带 RWX 授权）上 JIT 实际工作（机器码速度，探针判定"JIT 生效"）。无授权普通设备走纯解释器——该路径速度未测（待补）。JIT26 竞技场分支（m1-probe.yml + dualjit-arena.patch + rw17-jit26.js）封存为实验性全速分支，未验收。

已知小债：①"重新运行"按钮在进程内二次 coreclr_initialize → 0x80131022（CoreCLR 单实例），需改为提示重启 app 或 shutdown 后重建；②屏幕文案滞后（写 InterpMode=1 实为 2；初始化提示仍提 JIT26 握手）；③无授权设备的解释器吞吐数字待补。

**改造计划（2026-11-13 起，进行中）**：JIT 授予协议转 playport 模式——`brk #0xf00d` 同步握手 + 提前分离（不再长挂调试会话），见 [PLAN-JIT26.md](PLAN-JIT26.md)。

最小宿主 app + 自建 iOS CoreCLR + `Hello.dll`（Reflection.Emit 计时探针）+ mach RX 区域扫描。
**验收**：真机上，按下方流程开 JIT 后探针报"JIT 生效"（几十毫秒），RX 私有区域非零；port17-ui.log 里出现 `[rw17-arena] arena adopted`（brk 握手命中）。
**产出**：可下载的 `port17probe.ipa`。
**真机 JIT 流程（2026-11-13 起，JIT26 协议）**：
1. SideStore 安装 IPA（自签带 `get-task-allow`）；
2. 经 StikDebug 拉起探针 app（带 JIT）——runtime 在 `coreclr_initialize` 里发 `brk #0xf00d` 请求竞技场，最多等活调试器 120 秒（`[rw17-arena]` 进度在 stderr 日志）；
3. StikDebug 以本 app 为目标运行应答脚本 `probe/stikdebug/rw17-jit26.js`——在 app 停在 brk 上的窗口里经 debugserver `_M,rx` 分配 128MiB RX 并逐页扫写祝福（约 1–2 分钟），x0 回传地址，随后应答 `x16=0` 分离请求；**分离完成后脚本窗口可关**（祝福存续），app 在无调试器状态下继续初始化；
4. 日志期待链：`live debugger confirmed` → `arena granted at …` → `RW alias at …; detaching …` → `probe call #1 -> 42` → `probe call #2 -> 43` → `arena adopted: rx=… rw=…` → `CoreCLR 就绪` → `JIT 生效` → `exit 42`。

**装载连载沉淀的通用规则（后续任何"装了不生效"先查这十一条）**：

1. 任何 coreclr_initialize 位点必须先有竞技场，无竞技场一律干净降级不硬闯；
2. iOS 与安卓的宿主件位置不同（bundle vs 游戏目录），"next to the game"式查找必须加 bundle 回退——**iOS 上 `AppContext.BaseDirectory` 就是游戏目录**（engine.c 设 `APP_CONTEXT_BASE_DIRECTORY`），任何用 BaseDirectory 定位宿主件的补丁（PortHooks/PortMobile/MonoMod 的 shim 与 exhelper 同族）都要改走 `Port17HostFiles.Resolve`；
3. TPA 绑定按名字+版本+公钥精确匹配，且引用程序集不可执行——Framework 风格 mod 依赖的 mscorlib/netstandard facade 必须是可执行件（mscorlib 已换官方 facade；netstandard 实测本就是好件）。
4. Cecil 手写 IL 出包前必须在真实运行时执行一遍（`patch-harmony smoke <0Harmony.dll>`）：Cecil 写得出、ILSpy 反编译得干净，JIT 照样可能判 InvalidProgram——try/catch 里只能 `leave`，且 `leave` 目标要指向 `ldloc` 而不是 `ret`（0.4.10 真机代价一轮）。
5. iOS 上任何第三方库的可执行内存都必须来自竞技场（RX 地址执行、RW 别名写入，`Port17ArenaAllocator`），`__DATA_CONST` 的原地写与 `mmap(MAP_JIT|RWX)` 都不可用；MonoMod 这类库要接入就得替换它的 `IMemoryAllocator` 并让 `PatchData` 对竞技场地址走别名，而不是去修它的 Mach 内存代码（0.4.11→0.4.12）。
6. Android/Linux 专属 libc 入口（尤其 `gettid`）不能在共享 hooks/mobile 代码里直接 P/Invoke；线程身份统一走 `PortHooks.ThreadId.Current`，Linux 专用 `/proc`、affinity、perf-hint 只能留在平台分支内（0.4.13→0.4.14）。
7. IOS 后端的输入源是 Waylith `IOSWindow.HandleTouches`，不是 Android 版 `libglfw` 的 raw-touch 队列；接入 PortMobile 必须从 UIKit 原始事件取手指，并把 Touch 注入的 cursor/button/scroll 回接 `WindowBase` 注入 API。`touch mode managed` 只证明托管层打开了 shim，不证明 IOS 后端会把触摸交给它（0.4.14→0.4.15）。
8. 反射回读的装箱值先按声明类型 unbox 再做数值比较；装箱 `nint`（IntPtr）不实现 IConvertible，`Convert.ToInt64(object)` 会直接抛 InvalidCastException（0.4.16→0.4.17 真机代价一轮）。静态审查签名匹配不等于装箱转换路径安全。
9. 分层编译 tier-up 换热方法代码入口时静默丢弃 MonoMod/Harmony detour——混合 runtime 上默认 `DOTNET_TieredCompilation=0`（0.4.17→0.4.18）。"首次运行的日志"不能证明 hook 活着，hook 死活以心跳/计数为准；真机"功能从不生效"先查 hook 存活期，再查逻辑本身。
10. IOS 后端的 display link 只有在 `Window.FrameCallbacksEnabled` 为 true 时才被 `IOSPlatform.ScheduleNextIteration` 解除 paused；`WindowBase._frameCallbacks` 无初始值且全程序集无赋值点，`IOSWindow.SetFrameCallbacksCore` 为空实现，所以 display link 默认 paused，`PreferredFrameRate` 设置不参与主循环节拍。iOS 主循环实际是 run-loop timer（Continuous → 0 超时）+ `ThrottleToTargetFrameRate` 的 `WaitForBacklogAtMost(1)` + FIFO vsync；30fps 的裁决要看每帧 work/throttle/backlog 的分布，不能只看 `PreferredFrameRate` 日志（0.4.19→0.4.22 修正）。
11. IOS 后端不能把游戏选项的分辨率当作窗口 resize：`IOSWindow.RequestSizeCore` 未覆写、基类空实现。改 iOS 渲染负载也不能走宿主 GLFW shim 的 `glfwSetWindowSize`：`UIApplicationMain` 自己建 `IOSWindow`/`CAMetalLayer`，宿主那块 layer 不在屏幕上；要 patch `IOSWindow.HandleLayout`，把 view 的 `contentScaleFactor` 设成 `renderHeight/points`，让 `HandleLayout` 自己把 drawable 报成小尺寸（0.4.19→0.4.23）。

## 运行时 pin 升级规程

1. 改 `runtime-pin.txt` 第一行（commit 全 sha 或 `v11.0.0` 等 tag）；
2. push 后 Actions 自动重建 runtime 缓存（新 key）；
3. 在 PR/commit 里记录新 pin 对应的日期与来源分支。
